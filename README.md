# J-1 초안 10장 선택 규칙 · 정답 수집 · 평가

| 파일 | 하는 일 |
|---|---|
| `curation.py` | 선택 규칙 엔진. 6가지 방식으로 10장을 고르고 비교 화면(`compare.html`)을 만듭니다 |
| `labeler.py` | 앨범 주인이 정답(내 10장, 장면 구분, 꼭 필요한 장면)을 표시하는 HTML을 만듭니다 |
| `evaluate.py` | 각 방식의 10장이 주인의 정답을 얼마나 담았는지 계산합니다 |
| `params.json` | 규칙 파라미터. 개발용 앨범에서만 조정하고 평가 전에 고정합니다 |
| `tests/` | 단위 테스트, 가짜 앨범 생성기, 실제 CLIP 점검(`check_clip.py`), HEIC 점검(`check_heic.py`) |

원본 사진 폴더에는 아무것도 쓰지 않습니다. 결과와 캐시는 `j1_out\<앨범이름>_<해시>\`에 저장됩니다.

## 설치

```powershell
py -m pip install numpy Pillow pillow-heif onnxruntime huggingface-hub
```

CLIP 방식을 처음 실행하면 Hugging Face에서 `Xenova/clip-vit-base-patch32`의 `onnx/vision_model_quantized.onnx`(89.1MB, 입력 `pixel_values`, 출력 512차원 `image_embeds`)를 받아 `%USERPROFILE%\.cache\huggingface\hub`에 저장합니다. Python 3.14 + onnxruntime 1.32.0에서 동작을 확인했습니다. 처음 받을 때 Windows에서 symlink 경고가 나오는데 동작에는 문제가 없습니다.

`album_pilot.py`가 다른 ONNX 파일을 받았다면 `--clip-model 경로`로 같은 파일을 지정하세요. 두 스크립트가 같은 모델을 써야 유사도 기준값 0.92가 같은 의미를 갖습니다. 모델 없이 먼저 돌려 보려면 `--embedder none`(CLIP 방식 제외)이나 `--embedder tiny`(흐름 점검용, 보고 금지)를 쓰면 됩니다.

**처리 시간과 캐시:** 원본은 처음 한 번만 4개 스레드로 디코딩해 448px 무손실 PNG로 캐시합니다(`j1_out\...\work\`, 300장에 약 70MB). `labeler.py`, `curation.py`, `evaluate.py`가 이 캐시를 함께 씁니다.

| 휴대폰 크기(4032x3024) 사진 | 원본 디코딩 1장당 (4개 스레드) | CLIP 임베딩 1장당 |
|---|---|---|
| JPEG | 약 10ms | 약 90ms |
| HEIC | 약 250ms (순차로는 0.8~1.2초) | 약 90ms |

- **HEIC 40장 실측:** `labeler.py` 16.8초(원본 디코딩 포함), 이어서 `curation.py` 5.4초(CLIP 포함)가 걸렸습니다.
- **300장 추정:** HEIC면 처음에 약 2분 + 30초, JPEG면 1분 이내입니다.

사용성 실험에서 시간을 잴 때 이 대기를 포함할지, 미리 계산해 둘지 정하고 논문에 적으세요.

**아이폰 사진:** 케이블로 PC에 옮기면 '설정 > 사진 > Mac 또는 PC로 전송'이 '자동'일 때 JPEG로 바뀝니다. AirDrop이나 iCloud로 받으면 HEIC 그대로 옵니다. 두 경우 모두 처리되지만, 같은 실험 안에서는 한 가지로 맞추는 편이 깔끔합니다.

## 순서: 정답이 먼저입니다

### 1. 개발용 앨범 (오늘 파일럿 앨범)

```powershell
py labeler.py "C:\Photos\파일럿앨범"
```

`j1_out\...\label_*.html`을 크롬이나 엣지로 열어 앨범 주인이 표시합니다. 파일럿에서 휴대폰으로 고른 10장이 있으면 그 사진에 ★를 표시합니다. [라벨 저장]을 누르면 `labels_*.json`이 다운로드 폴더에 저장됩니다.

```powershell
py curation.py "C:\Photos\파일럿앨범"
```

`compare.html`에서 방식별 10장을 보고, `groups_time_clip.json`에서 묶음이 어떻게 나뉘었는지 확인합니다. 파일럿 관찰에서 사용자가 고민한 네 장이 한 묶음인지, 둘 다 남긴 단체사진과 풍경이 갈라졌는지가 핵심입니다. `params.json`을 고친 뒤 아래처럼 다시 돌리면 됩니다. 개발용 앨범에서는 몇 번을 돌려도 괜찮습니다.

```powershell
py evaluate.py "C:\Photos\파일럿앨범" "$HOME\Downloads\labels_파일럿앨범_xxxxxx.json" --params params.json
```

### 2. 파라미터 고정

평가용 앨범을 돌리기 전에 `params.json`을 확정하고, 출력에 나오는 `params_hash`(예: `b1c2d3e4`)를 기록해 둡니다. 이 값은 파라미터와 규칙·특징 코드 버전(`ENGINE_VERSION`, `FEATURE_VERSION`)으로 만들어지므로, 발표에서 "평가 전에 고정했다"는 근거가 됩니다. 규칙 코드를 고쳤다면 `curation.py`의 `ENGINE_VERSION`도 올리세요.

### 3. 평가용 앨범 (다른 여행 2~3개)

1. `py labeler.py "앨범"`을 실행해 앨범 주인에게 **label 페이지만** 줍니다. `compare.html`은 정답을 받기 전에 보여주지 않습니다.
2. 라벨 파일을 받은 뒤 평가합니다. 이 단계에서는 파라미터를 다시 바꾸지 않습니다.

```powershell
py evaluate.py "C:\Photos\제주" labels_제주.json "C:\Photos\부산" labels_부산.json --params params.json
```

평가 결과는 표로 출력되고 `j1_out\eval_<params_hash>.csv`에도 저장됩니다. 방식별로 놓친 장면 이름도 함께 출력되니 발표의 사례 분석에 쓰면 됩니다.

## 비교하는 방식

| 방식 | 묶기 | 다양성 감점 | 역할 |
|---|---|---|---|
| `random` | - | - | 하한선. 시드 200개의 평균 ± 표준편차 |
| `uniform` | - | - | 촬영 순서대로 일정 간격으로 10장. 심사에서 가장 먼저 물을 비교 |
| `time` | 시간 간격 30초 | 시간 | 시간만 쓰는 기준선 |
| `time_clip` | 시간+CLIP | 시간 또는 CLIP | **제안 방식** |
| `clip_group_only` | 시간+CLIP | 시간 | 분리 실험: CLIP을 묶기에만 사용 |
| `clip_div_only` | 시간 간격 30초 | 시간 또는 CLIP | 분리 실험: CLIP을 다양성에만 사용 |

`time`, `time_clip`과 두 분리 실험은 2x2 구조입니다. CLIP이 묶기와 다양성 중 어디서 도움이 됐는지(또는 안 됐는지) 따로 말할 수 있습니다.

네 방식이 공통으로 쓰는 고르기 규칙은 다음과 같습니다.

1. **대표 컷:** 묶음마다 가장 선명한 사진(라플라시안 분산 최대)을 대표로 씁니다. 표정 점수는 쓰지 않습니다.
2. **자리 배분:** 하루마다 촬영 장수에 비례해 10자리를 나눕니다. 새벽 4시 전 사진은 전날로 칩니다.
3. **중요도:** 묶음 크기(같은 장면을 몇 번 다시 찍었나)와 전후 5분 촬영량(그 무렵 얼마나 많이 찍었나)을 평균합니다.
4. **고르기:** `중요도 - 0.7 x (이미 고른 사진과의 최대 유사도)`가 큰 묶음부터 하나씩 고릅니다.

## 지표

장면은 모두 **앨범 주인이 나눈 장면**을 기준으로 셉니다. 우리 묶음 결과로 채점하면 자기 채점이 되기 때문입니다.

| 지표 | 정의 |
|---|---|
| 주인 장면 적중 | 주인이 고른 10장이 속한 장면 중 초안이 한 장 이상 담은 장면 수 / 그 장면 수. 같은 장면이면 다른 컷이어도 적중입니다 |
| 필수 장면 적중 | '꼭 필요' 장면 중 초안이 담은 장면 비율 |
| 장면 중복 | 초안 10장 중 이미 들어간 장면과 겹치는 장 수 (낮을수록 다양) |
| 같은 사진 | 주인이 고른 사진과 정확히 같은 사진 수 (참고용) |

앨범이 2~3개뿐이라 유의성 검정보다 앨범별 결과와 놓친 장면 사례를 보여주는 편이 정직합니다.

## 파라미터 (`params.json`)

| 키 | 기본값 | 의미 |
|---|---|---|
| `time_gap_sec` | 30 | 시간 묶음: 앞 사진과 간격이 이보다 크면 새 묶음 |
| `clip_window_sec` | 120 | 시간+CLIP 묶음: 이 시간 안에 사진이 추가된 묶음만 합칠 후보 |
| `clip_sim` | 0.92 | 시간+CLIP 묶음: 코사인 유사도가 이 값 이상이면 같은 묶음 |
| `day_start_hour` | 4 | 이 시각 전 사진은 전날로 셈 |
| `importance` | both | size / density / both |
| `density_window_min` | 5 | density에서 보는 전후 시간(분) |
| `rep` | sharp | 대표 컷: sharp / first / middle |
| `lambda` | 0.7 | 다양성 감점 세기 (0이면 중요도만) |
| `time_tau_min` | 30 | 시간 다양성: 시각 차이가 이 척도보다 작을수록 크게 감점 |
| `clip_div_floor` | 0.7 | CLIP 다양성: 유사도가 이 값 이하면 감점 없음 |

## 확인한 것과 아직 확인하지 않은 것

- **확인함:** `py tests/test_rules.py` 단위 테스트 8개 통과. 테스트한 항목은 다음과 같습니다.
  - EXIF 시각·시간대 파싱
  - 섞여 찍힌 단체사진·풍경 분리와 50초 뒤 재촬영 합치기
  - 날짜별 자리 배분과 다양성 감점
  - 장면 채점
- **확인함:** 가짜 앨범(사진 74장, EXIF 없는 PNG 1장, 깨진 파일 1장)으로 선택 → 정답 페이지 → 평가까지 전체 흐름이 돌았고, 원본 파일은 바뀌지 않았습니다. 정답 페이지의 ★ 선택, 장면 나누기·합치기, 새로고침 뒤 복원, 불러오기가 브라우저에서 동작했고, 저장한 라벨이 evaluate.py 입력과 일치했습니다.
- **확인함 (실제 CLIP, `tests/check_clip.py`):** 공개 샘플 사진 12장(scikit-image·matplotlib 내장)으로 측정했습니다.

  | 비교 | 코사인 유사도 (최소 / 중앙 / 최대) | 0.92 이상 |
  |---|---|---|
  | 연사 흉내 (1~3% 이동, 밝기 변화, 재압축) | 0.923 / 0.979 / 0.993 | 100% |
  | 재촬영 흉내 (70~85% 영역 다시 잡기) | 0.875 / 0.956 / 0.988 | 87.5% |
  | 서로 다른 사진 | 0.313 / 0.517 / 0.967 | 1.5% |

  - 서로 다른 사진 중 0.967이 나온 쌍은 같은 오토바이를 조금 옆에서 찍은 스테레오 사진이라 높은 게 맞습니다.
  - 의미 구조도 상식과 맞았습니다. 그레이스 호퍼 사진과 가장 가까운 것은 우주비행사(인물 사진끼리), 우주비행사와 가장 가까운 것은 로켓이었습니다.
  - 이 사진들로 만든 가짜 앨범(66장, 장면 12개)에서 시간 묶음은 21개였고, 섞여 찍힌 두 장면을 한 묶음으로 합쳤으며, 70초 뒤 재촬영 10건을 모두 따로 떼었습니다. 시간+CLIP 묶음은 정확히 12개였고, 섞인 장면을 분리했으며, 재촬영 10건을 모두 연사와 합쳤습니다.
- **주의:** 위 연사·재촬영은 이미지를 잘라 흉내 낸 것입니다. 실제 연사에는 사람의 움직임과 눈 깜빡임이 있어 유사도가 더 낮을 수 있습니다. 실제 여행에서 가장 헷갈릴 '같은 장소의 다른 구도'(단체사진과 바다 풍경)는 이 테스트에 없습니다. 0.92는 개발용 앨범의 `groups_time_clip.json`을 보고 다시 정하세요.
- **주의:** 가짜 앨범에서 `time_clip`은 '오토바이 왼쪽' 장면을 놓쳤습니다. 40분 떨어진 다른 장면인데 생김새가 거의 같아서 CLIP 다양성 감점을 받았기 때문입니다. 실제 여행에서도 '서로 다른 날의 비슷한 해변'이 이렇게 빠질 수 있습니다. `clip_div_only`와 `time`을 비교하면 이 감점이 득인지 실인지 볼 수 있습니다.
- **확인함 (HEIC, `tests/check_heic.py`, pillow-heif 1.8.1 / libheif 1.23.6):**
  - **촬영 시각:** HEIC에서도 DateTimeOriginal, 시간대, 1/100초를 JPEG와 똑같이 읽습니다.
  - **회전:** 세로 사진(Orientation=6)은 pillow-heif가 열 때 한 번 돌리고 EXIF 회전값을 1로 바꿉니다. 그래서 두 번 돌아가지 않고, 결과가 같은 JPEG와 픽셀 수준에서 일치했습니다(일치도 1.000).
  - **묶음 결과:** 샘플 앨범 66장의 절반을 HEIC로 바꿔도 시간 묶음(21개)과 시간+CLIP 묶음(12개)의 구성이 JPEG 때와 완전히 같았습니다.
  - **깨진 파일:** 중간이 잘린 파일은 건너뛰고 실패 목록에 표시합니다.
- **고친 문제:** 처음에는 캐시를 JPEG(품질 92)로 저장했습니다. 그랬더니 같은 사진의 CLIP 유사도가 0.95까지 떨어지고 사진 쌍의 유사도가 최대 0.09나 흔들려서, 샘플 앨범의 재촬영 한 장이 묶음에서 떨어져 나갔습니다. 무손실 PNG로 바꾼 뒤에는 원본에서 바로 계산한 값과 같아졌습니다. 같은 이유로, **같은 사진이라도 JPEG 재압축만으로 유사도가 0.03~0.05 흔들릴 수 있다는 점**을 염두에 두고 0.92를 정하세요.
- **아직 안 됨:** 실제 아이폰이 찍은 HEIC 파일은 써 보지 않았습니다. 테스트 파일은 pillow-heif로 만든 것이고, 회전을 아이폰과 같은 방식(파일 안의 회전 정보)으로 저장했습니다. 가짜 앨범 두 개의 점수는 장면 크기와 간격이 인위적이라 의미가 없습니다.

다음 단계인 '빠진 장면 복구' UI에는 `groups_time_clip.json`(묶음별 멤버와 대표 컷)과 `picks.json`을 쓰면 됩니다. 초안 10장에 대표가 하나도 들어가지 않은 묶음이 '미포함 묶음' 후보입니다.
