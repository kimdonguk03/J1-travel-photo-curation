# 실험 기록과 남은 검증

추천 규칙을 어떤 순서로, 어떤 근거로 바꿨는지와 앞으로 할 검증을 정리합니다. 규칙과 지표의 정의는 [recommendation.md](recommendation.md)에 있습니다.

## 데이터

| 데이터 | 쓰는 곳 | 비고 |
|---|---|---|
| 개발 앨범 2개 (경주 522장, UNIST 173장) | 규칙 설계, 파라미터 조정 | 주인이 중요 장면 10개와 직접 고른 10장을 표시. 개발 중 계속 들여다본 앨범이라 **최종 성능 근거로 쓰지 않습니다** |
| Photo Triage (사진 12,522장, 사람 판단 쌍 12,558개) | 대표 컷 고르기 외부 검증, 순위 모델 학습 | 개인 앨범 연사에서 사람이 고른 쪽을 모은 공개 데이터 |
| 평가 앨범 (예정) | 최종 검증 | 개발에 쓰지 않은 앨범. 파라미터를 고정한 뒤 정답을 받습니다 |

## 버전별 변화

| 버전 | 바꾼 것 | 바꾼 이유 |
|---|---|---|
| r1 | 시간 구간 + CLIP 유사도 0.92로 연사 묶기, 묶음 크기와 MMR로 10장 고르기, 날짜별 자리 배분 | 기준값 0.92는 사진 쌍을 직접 표시해 정했습니다(`pair_check.py`) |
| r2 | CLIP 문장 비교로 만든 **내용 점수** 추가 | 도로, 문서, 스크린샷처럼 보여줄 이유가 없는 사진이 초안에 들어왔습니다 |
| r3 | **방향별 선명도**, 대표 컷을 가장 선명한 컷으로, 관련도에 화질 점수 추가 | 연사 중 흔들린 컷이 대표로 뽑히는 경우가 있었습니다 |
| r4 | **LAION 미적 점수** 추가, 대표 컷을 **Photo Triage로 학습한 순위 모델**로 | 공개 연구의 사람 평가를 반영하고, 대표 컷 규칙을 외부 데이터로 검증하기 위해서입니다 |

## 실험

### 1. 선명도 측정 방식 (r3)

- **문제:** 기존 라플라시안 분산은 네 방향을 합쳐 재기 때문에, 한 방향으로만 흔들린 사진은 다른 방향의 디테일이 남아 값이 크게 떨어지지 않습니다.
- **방법:** 가로, 세로, 두 대각선 방향 2차 미분의 분산을 각각 구해 가장 작은 값을 씁니다.
- **검증:** 개발 앨범 사진에 인공 손떨림(직선 모션 블러)을 넣어, 흔들린 사진과 원본을 구별하는 AUC를 비교했습니다. 가로·세로 방향 흔들림에서 0.90 → 0.99.
- **함께 확인한 것:** 앨범 전체에서 선명도가 가장 낮은 사진은 흔들린 사진보다 흰 벽, 하늘, 얼굴 클로즈업이 많았습니다. 그래서 선명도를 절대 기준값으로 거르지 않고, 같은 묶음 안 비교와 앨범 안 백분위로만 씁니다.

### 2. 개발 앨범 비교 (r2 → r4)

값은 경주 / UNIST. 장면 적중과 같은 순간은 10개 중 개수, 백분위는 앨범 안 평균(0~100)입니다.

| 버전 | 장면 적중 | 같은 순간 | 선명도 백분위 | 미적 백분위 |
|---|---|---|---|---|
| r2 | 1 / 4 | 6 / 5 | 58 / 46 | – |
| r3 | 0 / 3 | 4 / 5 | 84 / 85 | 59 / 54 |
| r4 | 1 / 3 | 6 / 3 | 67 / 72 | 86 / 81 |
| 균등 추출 (기준선) | | | | 44 / 45 |

- r3에서 선명도는 크게 올랐지만 장면 적중과 같은 순간이 조금 내려갔고, r4에서 미적 점수를 더해 일부 되찾았습니다.
- 앨범이 2개, 장면이 10개씩이라 1~2개 차이는 우연일 수 있습니다. 이 표는 방향을 정하는 데만 썼습니다.

### 3. 주인이 고른 사진을 각 점수가 얼마나 가려내나

주인이 고른 10장과 나머지 사진을 점수 하나로 구별하는 AUC입니다(0.5는 무작위).

| 점수 | 경주 | UNIST |
|---|---|---|
| 미적 점수 (LAION) | 0.56 | 0.68 |
| 내용 점수 | 0.51 | 0.71 |
| 선명도 | 0.47 | 0.50 |

선명도는 "어떤 장면을 보여줄까"를 거의 설명하지 못합니다. 그래서 선명도는 같은 장면 안에서 컷을 고를 때 주로 쓰고, 장면을 고를 때는 내용 점수와 미적 점수의 비중을 함께 둡니다.

### 4. 앨범 범위

초안이 앨범 전체를 얼마나 덮는지(앨범 사진마다 가장 비슷한 초안 사진과의 유사도 평균)도 재 봤습니다. UNIST, K=5에서 r3 0.664, 균등 추출 0.772로, 제안 방식이 균등 추출보다 낮았습니다. 점수가 높은 장면에 자리를 주다 보니 덜 찍은 구간이 빠지는 것으로 보이며, 알려진 한계로 둡니다.

### 5. 외부 검증: Photo Triage (r4)

- **과제:** 비슷한 사진 묶음에서 사람이 더 좋아한 사진 맞히기. 우리 추천의 "묶음 안 대표 컷 고르기"와 같은 과제입니다.
- **방법:** 선명도, 미적 점수, 내용 점수를 각각 기준으로 써 보고, 쌍 비교 로지스틱 회귀 3가지(특징 3개 / 문장 15개 / CLIP 512차원 포함)를 학습했습니다. CLIP은 고정합니다.
- **나누기:** train 묶음의 15%를 시험용으로 떼어 두고, 공식 val에서도 따로 쟀습니다.
- **채택 기준(실행 전에 정함):** 두 시험 모두에서 선명도보다 쌍 정확도가 3%p 이상 높고, 1등 정확도도 오를 것.

| 방식 | 시험 묶음 쌍 / 1등 | 공식 val 쌍 / 1등 |
|---|---|---|
| 무작위 | 0.488 / 0.414 | 0.525 / 0.446 |
| 선명도 (r3 규칙) | 0.617 / 0.554 | 0.587 / 0.482 |
| 미적 점수 | 0.589 / 0.522 | 0.616 / 0.508 |
| 학습: 선명도+미적+내용 | 0.635 / 0.547 | 0.620 / 0.528 |
| **학습: + CLIP 512 (채택)** | **0.655 / 0.586** | **0.705 / 0.651** |

- CLIP 512 모델만 기준을 통과해 대표 컷 규칙으로 채택했습니다. 시험 묶음에서 선명도 대비 쌍 +3.8%p, 1등 +3.2%p입니다.
- 공식 val은 쌍이 482개라 오차가 ±2%p 정도이므로, 개선 폭은 시험 묶음 수치로 봅니다.
- 선명도 하나만으로도 무작위보다 확실히 나아서, r3의 "대표 컷은 선명한 컷" 규칙이 사람 판단과 맞는 방향이었음을 외부 데이터로 확인했습니다.
- 전체 표는 [recommendation.md](recommendation.md#외부-검증-photo-triage)와 [results/triage_result.csv](results/triage_result.csv)에 있습니다.
- 개발 앨범(경주)에 적용하면 2장 이상 묶음 88개 중 43개의 대표 컷이 바뀌었습니다. 직접 확인해 보니 대부분 같은 자세의 거의 같은 사진 사이의 교체였고, 흔들린 컷을 고른 경우는 없었습니다.

## 남은 검증

파라미터는 지금 `model/params.json`(`rule_version` `r4/clip_vision_model_quantized/a4a8ad41`)으로 고정하고, 아래 결과를 본 뒤에는 바꾸지 않습니다.

1. **평가 앨범으로 최종 비교**
   - 개발에 쓰지 않은 여행 앨범 2개 이상을 정합니다.
   - 앨범 주인이 추천을 보기 전에 정답 페이지(`labeler.py`, 노트북 3번)에서 중요 장면과 10장을 표시합니다.
   - 비교 평가(`evaluate.py`, 노트북 5번)로 제안 방식, 시간만 쓴 묶기, 균등 추출, 무작위를 비교합니다.
2. **초안 평가**
   - 같은 앨범과 개발 앨범에서 초안 평가(`draft_review.py`, 노트북 6번)를 합니다.
   - 제안 방식, 화질·미적 점수를 끈 방식, 균등 추출의 수용률과 '흔들림·흐림' 수를 비교해, 선명도·미적 점수가 실제로 건질 사진을 늘리는지 확인합니다.
3. **기여도 비교 (ablation)**
   - 평가 앨범에서 미적 점수, 화질 점수, 내용 점수, 학습 순위 모델을 하나씩 끄고 지표 변화를 봅니다. 파라미터는 고정한 채로 비교만 합니다.
4. **편집 경험**
   - 참가자 본인의 앨범으로 직접 선택과 추천 편집을 순서를 바꿔 수행하고, 확정까지 걸린 시간과 만족도(1~5점)를 기록합니다.
5. **서비스 연동 확인**
   - 실제 앨범으로 앱에서 불러오기부터 확정까지 한 번에 실행해, 처리 시간과 오류가 없는지 확인합니다.
